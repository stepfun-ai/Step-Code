# Agent 会议室 · 最终方案

> 状态：设计定稿，尚未实现。文中描述的是“打算做什么”，不代表当前代码行为。
> 可行性依据见 [飞书载体可行性调研](research/2026-10-22-agent-room-feishu-feasibility.md)，其中 §12 是在真实租户里跑出来的实测记录。
> 现状里的同类能力是 [当前会话的飞书连接](lark-connection.md)，它做的是“单聊远程遥控”，与本方案方向相反、可复用的部分是连接层。

## 1. 一句话

每个人有一个属于自己的飞书机器人。两个人在飞书上建一个群，各自 @ 自己的机器人，两台机器上的 session 就带着各自的代码、文件、环境开始对话。

## 2. 三个事实决定了方案形状

1. **价值来自信息不对等。** 两个 session 跑在两台电脑上，能看到的东西不一样。一次有效的交流不需要搬家上下文，只需要传递结论。这决定了产出应该是**带出处的结论**，而不是共享一份对话记录。
2. **载体是飞书群，因为人随时可以纠正。** 发言权用 @ 显式传递，机器逻辑和人的直觉是同一套，人不需要学任何东西就能插手。
3. **对外只有一个机器人，但它要服务多个群。** 分发和隔离是 Phase 1 就必须做的，不是以后的事。

## 3. 角色与拓扑

| 角色 | 数量 | 说明 |
| --- | --- | --- |
| 人 | 每人 1 | 拥有自己的终端与 session，是最终决策者 |
| 机器人 | 每人 1 | **应用机器人**（不是群自定义机器人），一键创建，一套凭证服务多个群 |
| 会议室 | 每次 1 个群 | 飞书普通群（`chat` 模式），成员 = 两个 bot + 两个人 |
| 绑定 | `chat_id → session_id` | 一对一。一个群只属于一个 session，一个 session 在 Phase 1 只服务一个群 |

两个 session 的 context **不合并**：各自的 workspace、model、权限、账单都独立，共享的只有群里的消息流。

## 4. 流程总览

命令叫 `/room`：在一个**已经打开的会话**里发起，代表“这个 session 要加入一个会议室”。

```
A 已有会话：/room
     │ ①无机器人则先创建（扫码授权 + 后台配置，见 §5）
     │ ②弹出 8 位房间码，终端等待
     ▼
A ──(当面念 / 发消息)──▶ B 通过分享链接或 /room join 48291730
                              │ ③B 顺带完成自己的机器人创建
                              │ ④登记 B 的 App ID 与 open_id
                              ▼
A 的机器人建群 ─────────────────────────────────────▶ 群已就绪
     │ ⑤一次拉齐：B 的 bot、A、B 两个自然人
     ▼
双方终端各自确认 → 绑定建立
     │
     ├─ A 侧：当前会话直接开战
     └─ B 侧：新开一个会话，名字叫 chat with A（见 §7.0）
     │
     ▼ ⑥A 在群里 @ 自己的 bot：「把初步调研结论给 B 发一下」
A 的 session 产出 → A 的 bot 回复并交棒 → B 的新会话接棒 → ……
```

两边的会话形态不对称，这是有意的：

| 发起方 A | 被邀请方 B |
| --- | --- |
| 用**已有的**会话发起 | **新建**一个会话，名字 `chat with <A 的名字>` |
| 上下文就是原本在做的事 | 上下文从零开始，只带自己那边的环境和这条消息 |

不对称带来一个必须处理的问题：**A 的会话一旦进入会议室，它原本在做的事就被占领了。** 所以 `/room` 发起后要明确提示 A，并支持房间结束后回到原始上下文（见 §7.7）。

## 5. 第 1 步：发现或创建专属机器人

### 5.1 目标

每个人**有且只有一个**「StepCode 会议室」机器人，重复执行不产生第二个。

### 5.2 现状与缺口

- 仓库已有 `LarkRegistration`，走官方 launcher 设备码协议（`archetype: "PersonalAgent"`），**授权后返回的是 `app_id` + `app_secret`**。
- 但主流程里没有持久化：凭证用完就丢（见 `apps/cli/src/ui/runtime/lark-connection.ts` 的 pairing 流程），所以现在**每执行一次 `/connect lark` 都会得到一个新应用**。

这正是第 1 步要补的东西：**把“一次性的配对”改成“一次性的创建 + 长期持有”**。

> **待验证**：launcher 协议只看到“创建”，没有列出或按名字发现已有应用的接口。要真正做到“发现”，要么飞书有查询能力，要么我们本地记住。下面的设计按“本地记住”来写，否则这一步做不了。

### 5.3 必须说清楚：机器人不是“配置一次就完了”

有一个误解要先拆掉：**每个用户要的不是我们预先配好、发给他用的机器人，而是他自己飞书身份下的一个应用**。`app_id` / `app_secret` 是个人身份下的凭证，我们无法替所有人铸好一套发下去。

所以第 1 步的“创建”是一个**面向用户的上手流程**，不是一个我们这边做完的配置动作。我们能在代码里自动化的部分，和必须由平台人工完成的部分，边界如下：

| 环节 | 能否自动化 | 依据 |
| --- | --- | --- |
| 创建应用 + 拿 `app_id` / `app_secret` | ✅ 设备码授权，一步 | `LarkRegistration` 已有实现 |
| 开启机器人能力 | ⚠️ 看协议 | 需要实测 launcher 创建的应用是否默认带机器人能力 |
| 申请 IM 权限（§10 那 6 个） | ❌ | launcher 只能预置**事件订阅回调**（`addons.callbacks`），不能预置权限；权限要在开发者后台申请，企业应用可能需要管理员审批 |
| 发布应用版本 | ❌ | 后台操作 |
| 事件订阅走长连接 | ❌ | 后台配置 |
| 建群、收发消息 | ✅ | 有了上面几步就行 |

这意味着一个绕不开的现实：**第一版会让每个用户在飞书后台点几下**，拿到一个凭证，承认一次。我们能把体验压到“扫一次码 + 后台点几下”，但压不到“零配置”。

如果某天出现“launcher 创建的应用默认自带机器人能力和事件订阅、权限可随包申请”的新形态，这几步才能合并。这本身就是一个值得向平台方确认的问题。

### 5.4 设计：凭证在哪、怎么复用

**凭证落在本机，不进仓库、不进任何远端。** 沿用仓库既有惯例（目录 `0o700`、文件 `0o600`）：

```
<storage root>/lark/room-agent.json
{
  "appId": "cli_xxx",
  "appSecret": "...",
  "botOpenId": "ou_xxx",
  "botName": "StepCode · 会议室",
  "brand": "feishu",
  "createdAt": "..."
}
```

**`/room`（无参数即发起）的判定顺序**：

1. 读凭证文件 → 有则先 `getBotIdentity()` 校验，通过就复用，终端显示 `room · agent ready · @<bot name>`
2. 没有，或校验失败 → 发起设备码授权 → 显示二维码与验证链接 → 轮询
3. 授权成功 → 拿 open_id 与名字 → **写入凭证文件** → 继续生成房间码
4. 失败或过期 → 回到可重试状态，不留下半成品

按钮文案要诚实：**扫码那一步是“创建应用”，不是“登录”。** 用户得知道自己在飞书里多了一个应用，以及它需要几步后台配置。

### 5.5 需要补的能力

| 能力 | 现状 | 要做的 |
| --- | --- | --- |
| 设备码授权 | `LarkRegistration` 已有 | 不动 |
| 凭证持久化与校验 | 无 | 新增 `room-agent.json` 读写 |
| 二维码 | `createLarkPairingView` 已有 | 挪到共用位置 |
| bot 身份 | `LarkApi.getBotIdentity` 已有 | 不动 |
| 权限缺失的自检 | 无 | 首次绑定失败时把缺失的 scope 明确报出来，并给出后台链接，而不是只说“连接失败” |

## 6. 第 2 步：配对与建群

### 6.1 8 位房间码

| 属性 | 取值 | 理由 |
| --- | --- | --- |
| 形式 | 8 位数字 | 口念即可，微信面对面的同款体验 |
| 有效期 | 2 分钟 | 人当面念的数字，过期重生成 |
| 次数 | 一次性，配对成功立即作废 | — |
| 错误尝试 | 最多 3 次，超限作废 | 1 亿组合，不设上限就可枚举 |
| 绑定对象 | 发起方的 **session instance** | 不是用户：同一个人开两个终端就是两个 agent |

码只负责让两个 session 找到彼此，**不负责授权**。授权发生在双方终端各自的那一次确认。

### 6.2 会合点：这一步需要新基础设施

飞书不提供“按码查找用户/群”的能力（见调研 §9.1），所以码必须由一个中立的会合点保管。三个选项：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 最小会合服务 | 只存 `码 → (发起方, 加入方登记)` 的 KV，TTL + 限次，不含任何消息内容 | 要运维一个服务，语义最干净 |
| 复用飞书 | 发起方把码写进自己与 bot 的单聊，加入方从自己的单聊里查到码后，用自己的 bot 转发给发起方 bot | 零新服务，路径绕，且依赖双方都有 bot 单聊 |
| 人工对齐 | 码只做提示，双方各确认一次由人对齐 | 最省，风险压回人身上 |

**建议第一版用“最小会合服务”**：它只需要三四个接口（登记、查询、确认、过期），不碰 agent，也不存消息。

### 6.3 建群（由发起方的机器人一手完成）

为什么必须是发起方：

- 飞书要求建群调用方在群内
- “主动加入群”只支持公开群，私有群进不去
- 需要 `owner_id` 指向自然人，所以**这一步要用用户身份**（`user_access_token`），不能纯 bot

请求要点：

- `bot_id_list = [B 的 App ID]`（是 `cli_xxx`，不是 open_id）
- `user_id_list = [A 的 open_id, B 的 open_id]`
- `owner_id = A 的自然人 open_id`
- `restricted_mode_setting.status = false`（保密模式会让消息读不到）
- `uuid = 房间 ID`（10 小时内去重，避免重复点创建建出两个群）

**建群后必须再查一次成员列表**：`+chat-create` 的成功不保证 bot 真的进群了（实测教训，见调研 §12.1）。

### 6.4 绑定建立

1. 双方终端各自显示群名与成员，请 owner 确认「我的 agent 参与这个房间」
2. 确认后写入绑定表 `chat_id → session_id`
3. 未出现在绑定表里的群，收到 @ 一律丢弃并计数（见 §8.1）

## 7. 第 5 步细化：上下文怎么组织，人在哪一步起作用

这是整个方案里最需要说清楚的部分。

### 7.0 两个会话各自是什么

房间不是一个新的上下文容器，而是**两个已有 session 各自的一个输入输出通道**。

| | A 侧 | B 侧 |
| --- | --- | --- |
| 会话 | 发起 `/room` 的那个会话 | 新建，标题 `chat with <A>` |
| 名字来源 | 已有 | 建群后从群成员里拿 A 的自然人姓名 |
| workspace | A 原本的工作目录 | B 自己的当前工作目录 |
| 启动上下文 | 原本的全部历史 | **为空**：只有第一条进来的消息 |
| 模型 / 权限 / 账单 | A 自己的 | B 自己的，不共享 |

B 的会话标题由我们决定，但**用户可以改**。名字只是给人看的，绑定关系永远以 `chat_id → session_id` 为准，不靠标题识别。

**怎么给用户看**：A 侧是一次显式的模式切换（终端状态从 `session` 变成 `room · <群名> · @<bot>`），B 侧就是一个普通的会话。两端都能用 `/room leave` 解除绑定，会话本身保留。

### 7.1 一次交流的完整生命周期

以「A 让 B 看初步调研结论」为例：

| 步骤 | 谁 | 发生什么 |
| --- | --- | --- |
| 1 | **A（人）** | 在群里 @ **自己的** bot：「把初步调研结论给 @B的bot 发一下」 |
| 2 | A 的 bot | 收到 @ 事件 → 判定“轮到我” → 把这句当作一条 **user 消息**送进 A 的 session |
| 3 | A 的 session | 正常跑一轮：读本地文件、整理结论、生成要发出去的内容 |
| 4 | A 的 bot | 在群里回复，内容里 @ B 的 bot → **交棒** |
| 5 | B 的 bot | 收到 @ → 判定“轮到我” → 把这条内容作为 **untrusted 外部输入**送进 B 的 session |
| 6 | B 的 session | 正常跑一轮：结合自己那边的代码/文件给出判断 |
| 7 | B 的 bot | 回复 A 的 bot 并 @ 回去 → **继续交棒** |
| 8 | … | 重复 4–7，直到某条回复**不 @ 对方** |
| 9 | **A 或 B（人）** | 想纠正谁就 @ 谁 → **夺棒**，并中断对方正在生成的那一轮 |

### 7.2 人的三个作用点

| 作用 | 动作 | 为什么重要 |
| --- | --- | --- |
| **发起** | 由**发起方本人** @ 自己的 bot | 这是唯一能让 session 启动一轮的动作。机器之间不能凭空开始 |
| **纠正** | 任何时候 @ 任意一方 | 打断 + 强制转交发言权。这是“载体选飞书”的全部理由 |
| **收尾** | 停下来，或在群外确认产出 | agent 之间的“共识”默认不算数，见 §7.5 |

关键设计：**人的消息永远优先于机器消息**。人 @ A 时，无论 A 正在生成什么，都中断并响应人。

### 7.3 上下文边界

每个 session 只拿三类东西，不拿第四类：

| 类型 | 来源 | 处理 |
| --- | --- | --- |
| 人发的话 | 群里被 @ 到自己的用户消息 | 作为普通 user 消息进入 session |
| 对方的发言 | 对方 bot @ 到自己的消息 | **untrusted 外部输入**，按网页内容同级处理 |
| 自己的历史 | 自己的 session | 本来就在 |
| ~~整群聊天记录~~ | — | **Phase 1 不拿**：不订阅全群消息，不补洞 |

这个取舍有代价，写清楚：**对方 bot 不 @ 你时说的话，你看不到。** 因此协议强制要求“交棒必须 @ 对方”，把可见性和发言权绑在同一件事上。

### 7.4 谁来决定“说什么”

A 说「把初步调研结论给 B 发一下」时，**不是由脚本去读文件再拼一段话**，而是 A 的 session 正常跑一轮：它自己决定读哪些文件、怎么概括。这正是 agent 该干的事。

脚本负责的只有：把群里的话**送进** session、把 session 的输出**送出去**、以及决定**交不交棒**。

### 7.5 产出：带出处的结论，不是聊天记录

房间不会产出“一份决议”，因为两个 agent 互相认可的东西没有人背书。产出是一张卡片：

- **结论**：每条都标出处——「A 侧看到：SDK 是 1.76.0」「B 侧推断：因此 X」
- **分歧**：没有收敛的对立观点，保留双方原话
- **待确认**：需要人拍板的

**硬规则**：没有标出处的论断，一律归入“待确认”。这不是风格问题——两个 agent 互相确认时最容易产生看起来像事实的幻觉，而信息不对等恰恰意味着**每一方都在替对方补它看不到的部分**。

### 7.6 A 侧会话被占领的问题

A 在已有会话里执行 `/room`，这个会话就同时背着两件事：它原本的工作，和这场对话。处理不好会很难看——用户本来在写代码，突然群里的消息插进来，agent 开始回群里的问题。

建议的最小做法：

- **发起时明确告知**：`room · 已进入会议室 · 原任务将被暂停`，并给出退出方式
- **房间活跃期间**：群消息以 `followUp` 方式进入会话，不打断 A 原本正在跑的一轮；A 原本的下一轮开始时，系统提示里带上当前房间标识，避免 agent 混淆“我现在在跟谁说话”
- **`/room leave`**：立即解除绑定，后续群消息一律丢弃，会话回到普通状态
- **不自动回滚**：不替用户撤销房间里做过的事，只停止继续接收

B 侧简单得多：它本来就是一个新会话，退出即结束。

### 7.7 什么时候该停

不停数轮次，而是看**有没有新东西**：

- 连续 2 轮没有出现“另一方看不到的事实” → 空转，停
- 加一条兜底的连续 bot→bot 轮次上限（防协议失效时无限对拜）

## 8. 分发与隔离（Phase 1 必须做）

### 8.1 路由

每个入站消息只做一件事：`chat_id` 查绑定表，命中就投给对应 session，未命中就丢弃。

- **静默丢弃 + 计数**：未绑定的群不回复、不起 session、不调模型。计数给 owner 在终端看（`room · 3 个未绑定群收到 7 次 @`），不往群里说话。
- **没有隐式绑定**：把机器人拉进新群不会自动获得会话。绑定只能由 `/room`、`/room join` 产生。
- **收窄订阅**：只关心 @ 本 bot 的消息，判定用 `mentions[].mentioned_type === "bot"` 且 open_id 等于自己。

### 8.2 信任边界

| 规则 | 说明 |
| --- | --- |
| 对方 bot 的输出 = untrusted | 可以让本侧 agent 在群里发言、生成方案；**不能**触发工具权限提升或配置修改 |
| 权限归 owner 的终端 | 审批卡片必须标出是哪个群，且只能由该群绑定的 session 发起 |
| 决策令牌绑定到 `(chat, session, 那一次 UI 请求)` | 现有实现只校验 `chatId`，必须补 |
| @所有人 不是交棒 | 广播谁也没点名，任何 bot 都不应因此开一轮 |

## 9. 分阶段

| | Phase 1 | Phase 2 |
| --- | --- | --- |
| 绑定 | 一个群 = 一个 session | 一个 session 可挂多个群 |
| 订阅 | 只收 @ 本 bot 的消息 | 视需要补全量监听与补洞 |
| 权限 | `im:message.group_at_msg` + `send_as_bot` + 建群/拉人 | 追加 `im:message.group_msg`（敏感，需审批） |
| 分发 | 已做 | 不变，但隔离要求更高 |

## 10. 最小权限清单

产品应用只需要这些（详见调研 §12.6）：

| 权限 | 用途 |
| --- | --- |
| `im:message.group_at_msg` | 群里 @ 机器人时收到事件 |
| `im:message:send_as_bot` | 机器人发言 |
| `im:chat:create` | 建群 |
| `im:chat.members:write_only` / `:read` | 拉人、校验成员 |
| `im:message.reactions:write_only` | 进度与取消（可选） |
| `im:message.send_as_user` | 建群时以自然人做群主（一次性用户授权） |

**不申请** `im:message.group_msg`（Phase 2 再看），**不碰** OKR / 妙记 / 邮箱 / 日程 / 多维表格。

## 11. 拆到仓库里

`/room` 直接内建进 CLI，不做插件、不做外部扩展。它是一个产品命令，和 `/connect` 同级。

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 协议 | `packages/lark-adapter` | 建群、拉人、发文本、收发事件、去重排序。不持有 session 或 transcript |
| 路由 | `packages/coding-agent/src/features/step-room/` | 绑定表、交棒判定、事件排序 |
| 凭证 | `packages/coding-agent/src/step/` | 机器人凭证的创建、持久化与校验 |
| 命令与接线 | `apps/cli` | `/room`、`/room join`、`/room leave`，以及把群消息投进 session |

为什么不做插件（曾评估过，结论是不做）：

- 插件目前**带不了可执行的扩展代码**：`step.plugin.json` 里的字段不包含扩展入口，扩展加载器也不扫描插件目录。要做插件就得先改插件系统，成本高于收益。
- `/room` 需要拿到 session 生命周期、中断、权限决策——这些只有 CLI 进程内有。放进外部进程就意味着每次都要跨进程同步状态。
- 功能在测试期需要的是**快速迭代**，不是分发。等它稳定之后再谈要不要拆出去。

现有 `lark-adapter` 的 `LarkInboundGate` 是单群绑定，要改成注入一个 `resolveChat(chatId)` 回调：单聊行为传固定值保持不变，会议室传绑定表。

## 12. 现在就能做 / 等机器人才能做

**不需要机器人凭证**：

- 交棒判定、绑定表、事件排序（已完成，32 个测试）
- `LarkApi` 补建群、拉人、发文本、拉历史四个方法
- 凭证持久化的读写逻辑（用假凭证测）

**必须有已发布、配好事件订阅的应用**：

- 事件能否推送到群
- A bot @ B bot，B 是否收到
- 权限是否够用

## 13. 验收要点

Phase 1：

1. 第一次 `/room` 创建机器人并落盘；第二次直接复用，不产生第二个应用
2. 未绑定的群里 @ 机器人，不产生回复、不起 session、不调模型
3. 人在群里 @ 自己的 bot，该消息进入对应 session，产出回到群里
4. 对方 bot 的发言不会引起本侧任何权限请求
5. 一条消息 @ 两个 bot 时不出现双发言
6. 人 @ 一方时，该方正在生成的那一轮被中断
7. 决策令牌在群与会话不匹配时被拒绝
8. 被邀请方 B 侧新会话标题为 `chat with <A>`，且首轮上下文只含进来的那条消息
9. `/room leave` 之后，该群后续 @ 全部丢弃，不打断会话原有工作

Phase 2 追加：

10. 同一 session 服务两个群时，A 群的 untrusted 内容不会进入 B 群的上下文
11. 断线重连后 transcript 不重复、不缺口
