# StepCode 批量拓展分类、规范化与市场注册流程（V1 草案）

本规范供任意新会话、执行 Agent 或人工维护者使用：接收一批待分类拓展，逐项判定类型、按规范改造、验证实际能力，再注册到 StepCode 拓展市场。执行依据保存在项目规范、批次清单和逐项验收记录中，不依赖先前对话或个人记忆。交付文件和三类结构要求见[拓展包与市场展示规范](extension-package-standard.md)。

编制日期：2026-11-09。本规范定义操作流程，不代表现有条目已经通过审核，也不代表当前程序已经实现全部门禁。

## 1. 启动方式与执行边界

### 1.1 每个会话需要的输入

| 输入 | 要求 |
| --- | --- |
| StepCode 项目目录 | 提供当前可访问的项目路径，不假定沿用上一会话机器或目录 |
| 待分类拓展 | 提供批次目录、压缩包或明确文件清单；混合插件、技能、连接器可以一并提交 |
| 规范文件 | 同时读取本文件与配套拓展包规范，并遵守项目当前有效的 Agent 规则 |
| 批次输出目录 | 指定维护记录和规范化副本的保存位置；未指定时在项目外的独立本地批次目录保存，不写入用户运行配置 |
| 已有批次记录 | 续办时提供批次清单与报告路径；首次引入不要求提供 |
| 授权与目标范围 | 默认完成本地分类、适配、验证和市场注册；共享发布、个人环境安装和外部副作用不包含在该默认范围内 |

开始执行前，确认输入文件可访问，检查工作区已有修改，核对现有市场条目和实际加载、打包、安装代码。本文列出的脚本、字段和限制是编制时参考；新会话必须以当前代码确认是否仍适用，不能直接照用过期命令。

### 1.2 默认执行目标

用户提交一批待分类拓展并要求按本规范引入时，执行者应完成本地流程，而不是只输出建议：

1. 给每个输入分配批次条目编号，保留原始材料。
2. 先逐项给出明确上架类型和判定依据，再处理规范化改造。
3. 只对来源、许可、依赖和安全边界允许的条目继续执行。
4. 在独立环境完成接入与实际功能验证。
5. 将通过项注册到本地市场，交付结果清单及证据。
6. 单列阻塞、重复、排除和待验收项，不让一个条目阻断其他独立条目。

正常本地分类、结构检查和不改变既有介绍的规范化操作不必反复确认，但介绍文案设独立确认门禁：已有介绍默认原样保留；翻译、精简、改写或补充均先提交原文、候选文案、理由和证据，用户逐项或明确整批批准后才写入。一般性的“按规范改写”不授权批量覆盖介绍。未确认项保留原文，其他独立工作可继续；需要修正文案才能放行的条目等待确认。遇到许可不明确、核心能力必须裁剪、已有商品替换、缺少必要输入或外部副作用时，暂停对应条目并提出具体问题，不得自行扩大范围。

### 1.3 注册、安装和发布的区别

- **暂存接入**：在隔离副本或测试环境生成候选目录、payload 或 MCP 模板，用于验收，不代表正式市场已注册。
- **本地市场注册**：将通过项及其已验证资源接入当前项目的正式市场目录，核对最终产物与验收对象一致。
- **个人安装**：将拓展安装或配置到用户日常 StepCode 环境，默认不执行；验收只使用独立配置环境。
- **共享发布**：Git 提交、推送、创建 PR、分发安装包或修改线上市场，必须有单独授权。

上架必须同时满足：来源可追溯、分发有依据、展示一致、资源完整、配置明确、实际可用。能够浏览、文件安装成功、依赖就绪、认证完成和业务任务成功是不同结果，不能相互替代。

## 2. 批量引入标准流程

接收批次并盘点 → 逐项分类与去重 → 来源和许可核查 → 规范化改造 → 静态检查 → 暂存接入 → 实际验收 → 正式本地注册 → 批次交付与续办。

| 阶段 | 执行工作 | 必须落盘的结果 | 放行条件 |
| --- | --- | --- | --- |
| 接收与盘点 | 只读检查文件，识别包根目录和子包，保留原包与校验值 | 批次清单、输入编号、来源路径与原包哈希 | 每个输入可追溯，不遗漏，不执行未知包脚本 |
| 分类与去重 | 根据入口和实际能力判定插件、独立技能或连接器，与同批及已有市场比对 | 逐项类型、判定证据、重复或冲突结论 | 不照搬来源标签，不强行归类，不重复注册 |
| 来源与许可核查 | 核实作者、版本、许可、分发方式、依赖及可选 Logo 权利 | 许可依据、前置条件、阻塞原因 | 当前分发与接入方式有依据 |
| 规范化改造 | 在副本中修声明、路径、工具调用和依赖；已有介绍保留，确需调整时先提交前后对照，取得用户确认后再应用 | 规范化包、变更清单、文案提案及确认记录、适配版本 | 资源完整，介绍真实有意义，仅写入已确认改动，不依赖原平台私有环境 |
| 静态检查 | 校验入口、文件引用、元数据、许可、凭据风险和包体 | 检查命令、结果与未执行项 | 无阻断问题 |
| 暂存接入 | 生成候选 catalog、payload 或模板，处理可选 Logo | 候选资源与哈希、映射检查结果 | 目录、资源和配置一致，未混入正式注册结果 |
| 实际验收 | 在独立环境检查展示、安装或配置、代表任务和异常场景 | 逐项验收记录、真实产物或调用证据 | 必测项通过；未执行不计为成功 |
| 正式本地注册 | 将通过项合入当前项目市场，复核候选与最终交付的一致性 | 商品 ID、实际修改路径、最终校验结果 | 不覆盖未知已有修改，不发布失败项 |
| 批次交付与续办 | 汇总完成项和剩余项，记录下一步与所需输入 | 批次报告、清单最新状态、续办说明 | 任意新会话可以从记录与磁盘状态继续 |

分类结果中，能判定的条目必须先给出插件、独立技能或连接器之一；证据不足的条目写“待判定”，不强行注册。批次目录包含多个子包时拆成多个条目，保留父输入关系；不得默认拆出插件内所有技能作为独立商品。

批次执行状态建议为“待分类”“待审核”“待改造”“待验收”“已注册”“阻塞”“重复跳过”“排除”，仅用于维护记录，不代表市场 UI 已有这些状态。条目同时记录最后完成阶段、验收结果和注册结果；“阻塞”不能抹掉已完成的改造或测试事实。

同批条目可独立检查和改造，但对共享 catalog、模板脚本和 payload 的写入应统一合并，避免多个执行者互相覆盖。批次结束时，每个输入必须有明确结果。

## 3. 来源与权限审核

### 3.1 必查信息

- 原项目、真实开发者、来源市场和实际获取渠道。
- 上游版本、提交号或其他不可变来源标识。
- 代码、文档、图标、素材和附带第三方组件的许可证。
- 原样分发、修改分发、商业使用及远程服务接入的具体边界。
- 是否包含原平台专有依赖、私有端点或账户环境。
- 是否需要费用、配额、额外应用、账号和特殊权限。

### 3.2 放行规则

- 公开仓库、可下载、作者提供安装方式，不自动等于允许文件再分发。
- 没有明确许可证或授权依据时，不默认获准复制到 StepCode 市场。
- 有明确许可时，按许可履行署名、NOTICE、修改声明或源代码提供等义务。
- 提供 Logo 时，其权利与代码许可分别核查；未提供或无法获得图标使用授权时，省略 Logo 并使用类型默认图标，不因缺少 Logo 阻止上架。
- 远程服务接入不自动获得服务端代码的分发权。
- 无法核实的来源、许可或服务条款标记待审核，不作为正式上架条目。

## 4. 分类与原包归档

### 4.1 分类判定

按实际能力判定，不直接继承来源市场标签。插件内技能需要独立上架时重新核查资源依赖与许可，并建立独立验收记录。

技能调用 MCP 服务不等于技能本身就是连接器；只有通过 MCP 协议提供工具的服务或程序才按连接器接入。

### 4.2 原包留存

在维护资料中保留原始包、获取时间、固定版本或提交号、SHA-256 校验值及许可材料。适配工作使用单独副本，不修改原包。

分发包与原包分别计算校验值，记录差异。校验值用于内容一致性与追溯，不等于签名或安全认证。

## 5. 规范改造

### 5.1 允许的改造

- 转换为 StepCode 原生声明。
- 修复相对路径、资源引用和环境配置。
- 替换有明确等价实现的平台工具调用。
- 补齐触发条件、使用说明、异常处理和依赖声明。
- 已有介绍默认原样保留；英文翻译、精简、改写和缺失介绍补充先形成候选文案。原介绍只有包名、组件数量或套话时，依据已核实能力提出一句用途说明，经用户确认后才应用。
- 保持技术标识、命令、参数、环境变量、配置键、路径和包名不变，不在翻译中改变触发语义、执行步骤、权限或能力边界。
- 保留原介绍、候选文案、修改依据和用户确认范围；仅同步已确认的市场目录、详情摘要和相关分发文档，内容改变时更新版本、哈希和验收结果。未确认项不得先写入再征求同意。
- 按许可保留署名及许可原件，记录每项改动及原因，译文不代替原始许可材料。

### 5.2 禁止的改造

- 删除原作者署名或许可证。
- 将第三方适配包标为完全自研或官方。
- 复制原平台凭据、账号、私有服务配置。
- 删除权限检查以消除运行失败。
- 用占位数据、模拟结果或提示词冒充真实功能。
- 未准备依赖或完成授权，却宣称无需配置、直接可用。
- 擅自修改其他产品配置、全局环境或用户业务文件。

### 5.3 依赖与能力处理

逐项核对 CLI、MCP、其他技能、外部应用和平台专有能力。依赖固定版本、说明配置方法，并验证实际运行资源。

缺少等价能力时，明确限制或暂停引入，不得悄悄删除核心功能后保留原商品描述。涉及功能裁剪应重新确定商品能力边界。

## 6. 静态检查门禁

至少检查：

- 商品 ID 与运行标识唯一且相互匹配。
- manifest、SKILL.md 或 MCP 模板符合当前解析规则。
- 必填名称、介绍、版本、分类、文档及许可材料齐全。
- 已有合格介绍原样保留；候选中文介绍用一句话说明具体用途，不以名称、CLI 名称、组件数量或宣传词代替。每项实际文案改动须对应用户确认记录与能力证据，不承诺适配未支持的功能；用途不明时标记待核实。
- Logo 可选；提供时检查授权、格式和资源引用，未提供时省略 `logo` 字段并验收类型默认图标。声明 Logo 但资源缺失时，修复资源或移除声明后再验收。
- 所有执行和引用资源存在，路径位于允许范围内。
- 没有真实凭据、开发机绝对路径和无关仓库缓存。
- 没有符号链接、路径穿越、重复文件或大小写冲突。
- 依赖声明与文档一致，正式运行版本可复现。
- 包体符合插件或技能的现有安装边界。
- 展示组件数量、文档、版本和分发内容一致。

现有打包器对部分凭据样式和文件风险有检查，但不等于完整的代码、指令和内容安全审核。记录实际执行过的检查，未执行项明确标注，不得声称“已安全认证”。

## 7. 市场接入与打包同步

### 7.1 插件与独立技能

必须同步规范化资源、市场目录和可安装 payload。Logo 可选：提供时同步市场 Logo 资源与目录引用；未提供时省略 `logo` 字段，验收类型默认图标，不强制补图片。

当前相关实现：

- [市场目录](../apps/web/client/src/features/market/catalog/catalog.json)。
- [市场数据映射](../apps/web/client/src/features/market/extension-market-data.ts)。
- [插件打包脚本](../apps/web/scripts/package-plugin-market.mjs)。
- [技能打包脚本](../apps/web/scripts/package-skill-market.mjs)。
- [payload 复制脚本](../apps/web/scripts/copy-market-payload.mjs)。

插件与技能 payload 分别生成到 `apps/web/resources/plugin-market.json` 和 `apps/web/resources/skill-market.json`，Web 构建将其复制到编译后的 Host 旁边。资源生成后，核对包中条目、运行标识和商品 ID 的映射。

- 只更新市场目录，可能出现能浏览但无法安装。
- 只更新 payload，可能出现展示与实际安装内容不一致。
- 技能内容改变后同步文档、哈希和版本。
- 新增 `entry`、`agents` 或额外运行文件时，单独核查打包和加载链路，不假定打包器覆盖全部资源。
- 使用重建后的 Host 验收，不使用此前进程缓存的 payload 结果代替新版本检查。

当前 payload 与源码目录分别交付，缺失 payload 时可以浏览但安装不可用；边界见[插件市场安装说明](plugin-market.md)。正式交付必须确认 payload 实际进入交付产物。

### 7.2 连接器

必须同步市场目录、详情文档、固定 `serverName`、配置模板、模板来源证据、运行环境和认证说明。Logo 可选：提供时同步图标资源与引用；未提供时使用地球图标，已知为本地 stdio 时使用终端图标。

当前连接器以[模板脚本](../apps/web/scripts/package-connector-templates.mjs)维护接入建议，不采用插件或技能 payload 的安装方式。打开模板不等于服务已安装或已启动。

配置必须符合[当前 MCP 解析器](../packages/coding-agent/src/step/mcp-settings-secrets.ts)。本地启动与远程端点二选一；官网、源码和文档地址不能替代服务端点。

## 8. 实际使用验收

### 8.1 环境要求

- 使用独立配置环境和测试工作区，不借用原平台配置或开发机缓存。
- 记录系统、架构、运行时、外部应用及依赖版本。
- 仅在测试数据、测试账户和明确授权范围内操作。
- 费用、网络下载、外部写操作和认证流程提前说明并取得相应授权。
- 不在用户真实项目或共享业务系统中默认执行验收。

### 8.2 三类共用用例

| 检查项 | 成功标准 |
| --- | --- |
| 列表与详情图标 | 名称、介绍正常显示；提供 Logo 时图片正确加载，未提供时显示规定的类型默认图标，无空白占位、破损图片或明显排版问题 |
| 介绍意义与中文化 | 一句话能独立说明该拓展的用途，中文自然且与已核实能力一致；不只描述组件数量，翻译不改变步骤或权限要求 |
| 搜索与分类 | 名称、介绍等已支持字段可搜索，分类与主要用途一致 |
| 商品详情 | 文档、版本、组件、前置条件与当前交付一致 |
| 干净环境准备 | 按文档可以完成安装或接入，不依赖开发机私有环境 |
| 核心业务任务 | 至少完成一个代表任务，核对真实输出或产物 |
| 缺依赖、缺凭据、网络失败 | 不报告成功，准确提示缺少的前置条件 |
| 禁用 | 不继续作为可用资源使用 |
| 卸载或移除配置 | 不影响无关拓展、凭据或用户业务文件 |

### 8.3 插件专项

- 安装后所有声明组件和被引用资源存在。
- 新建或重新加载会话后，技能与命令可用。
- CLI 依赖准备状态与实际结果一致。
- 包含 MCP 的插件完成初始化、工具发现和代表性工具调用。
- 额外入口与 agent 定义按当前运行链路单独验证，不能以文件存在替代执行成功。
- 不依赖原下载目录。

依赖准备完成与首次授权完成是不同状态，详见[插件 CLI 准备说明](plugin-cli-preparation.md)。

### 8.4 技能专项

- 触发条件有效，指令和工具调用方式适用于 StepCode。
- 引用脚本、素材和参考资料全部可访问。
- 实际产物符合约定，不只回复“已完成”。
- 前置依赖未配置时，提供准确指导，不伪造结果。
- 不影响无关技能或会话。

### 8.5 连接器专项

- 分别记录服务准备、认证、初始化、工具发现和实际调用结果。
- OAuth 连接器验证授权与授权失效场景。
- 涉及写操作时使用测试数据并明确授权。
- 外部应用型连接器验证应用侧插件、版本和启动状态。
- 服务中断显示失败，不继续宣称可用。
- 配置保存、端口可达、工具列表可见不能替代业务调用验收。

### 8.6 平台与结论

只公布已实测的平台范围。只验证 macOS 时，不得宣称 Windows 同样通过。

验收结论区分“通过”“失败”“未执行”“不适用”。正式上架范围内的必测项全部通过后才可放行；未执行和失败不能计为通过。

## 9. 验收记录最低内容

每个拓展保留：

1. 商品 ID、运行标识、适配版本、上游版本或提交号。
2. 原包和分发包的校验值。
3. 来源、许可证和审核依据；提供 Logo 时记录其权利依据，未提供时记录使用的类型默认图标。
4. 改造文件清单、原因及功能边界变化。
5. 测试日期、平台、运行时和依赖版本。
6. 前置配置方法，不记录实际密钥。
7. 用例、步骤、输入、预期结果、实际结果及产物证据。
8. 未执行检查、已知限制及未解决问题。
9. 审核人、维护负责人、交付版本和回退方案。

验收记录保存在维护资料中，不要求安装到用户运行目录。

## 10. 上架、更新与回退

### 10.1 上架条件

来源与分发依据、规范交付、资源一致性和真实功能验收全部通过。未完成授权审核或验收的条目不得作为正式可用商品发布。

建议内部使用“已收录”“待配置”“验收通过”“暂停分发”四种管理状态；这不是当前 UI 已实现的状态。用户需要首次配置与条目已完成维护者验收可以同时成立，不能把用户配置状态误判为商品审核结果。

### 10.2 更新要求

- 内容、依赖、配置和权限变化均记录版本与差异。
- 核心能力或运行依赖变化后重做相关真实验收。
- 许可证或来源变化后重新审核分发依据。
- 纯展示修改也需校验目录、文档与资源的一致性。
- 当前插件和技能安装器不会直接覆盖已安装同标识目录，不得宣称已有无损原地升级能力。

### 10.3 回退与暂停

保留上一份通过验收且仍获准分发的版本。新版本出现安装失败、核心能力失效或许可风险时暂停发布，核实受影响范围后按明确方案回退。

用户侧重新安装旧版本前，说明当前安装器的冲突规则并确认处理方式；不得擅自删除现有拓展、凭据或用户数据。授权失效的版本不能作为回退候选。

## 11. 现有项目需要补齐的自动门禁

以下为待实现事项，本轮文档不包含代码修改：

1. **取消固定技能数量限制**：技能打包脚本目前写死 36 个技能，新增条目会报错；默认分类也不能代替人工确认。
2. **减少连接器硬编码映射**：模板脚本维护固定目录和配方；新条目需要同步更新，并将正式依赖固定为可复现版本。
3. **增加目录与资源一致性检查**：覆盖唯一 ID、必填字段、可选 Logo 的授权与资源引用、文档、catalog 与 payload 一一对应；缺少 Logo 不报错。列表与详情的类型默认图标已实现并完成浏览器回归，其他资源一致性门禁和授权审核仍需完善。
4. **增加运行资源完整性检查**：覆盖脚本、入口、依赖文件和间接引用，不止检查 manifest 可解析。
5. **增加新增条目的真实验收门禁**：要求实际工具调用或产物证据，不能用构建成功替代业务可用。

## 12. 使用本规范的边界

文档制定不等于既有市场条目已经通过这些要求。既有条目需要另行审查；打包、安装安全边界也不等于完整安全认证。后续实现门禁、改造现有包或执行外部服务测试，应分别确定范围并记录验证证据。

本文是任意会话均可读取的操作依据，不需要依赖本次会话记忆。但会话仍须能够访问项目、规范及输入材料；跨机器时应一并迁移必要资料并替换本机路径，不能假定其他会话自动获得这些文件。

## 13. 批次记录与跨会话交付

### 13.1 维护资料结构

每次执行使用独立批次编号，建议采用日期加短名称。以下为建议结构，不是 StepCode 运行时自动读取的目录，也不要求本次文档编辑创建实际批次：

```text
<批次输出目录>/<批次编号>/
  batch-manifest.json
  batch-report.md
  originals/
  normalized/
  checks/
  acceptance/
```

- `originals/`：原包或不可变原包引用、版本及哈希；原始材料已可靠保存时不必重复复制。
- `normalized/`：逐项规范化副本，按输入编号分目录，不能依赖会话临时内存。
- `checks/`：静态检查和映射检查结果，日志脱敏。
- `acceptance/`：逐项实际验收记录、产物和必要截图，禁止记录凭据。
- `batch-manifest.json`：机器可读的执行清单。
- `batch-report.md`：人工可读的分类、改造、注册汇总和续办说明。

路径以批次目录或项目目录为基准记录，注明基准，便于跨机器迁移。每完成一个阶段或出现阻塞就更新清单，不只在会话最后汇总。

### 13.2 批次清单必需字段

| 范围 | 字段或记录 |
| --- | --- |
| 批次 | 批次编号、目标项目、输入范围、输出目录、规范版本或哈希、更新时间、授权边界 |
| 输入 | 条目编号、父输入编号（如有）、原始路径、原包或文件树哈希、上游来源及版本 |
| 分类 | 类型或待判定、判定依据、与同批和已有市场的重复或冲突关系 |
| 审核 | 许可依据、来源可信信息、依赖、权限、Logo 使用情况 |
| 改造 | 规范化副本路径、修改清单、原介绍与候选介绍、修改原因与能力证据、用户确认结果及批准范围、适配版本、分发哈希 |
| 检查与验收 | 结果、证据路径、测试环境、未执行项、阻塞原因 |
| 注册 | 商品 ID、运行标识、正式修改路径、注册状态、最终资源哈希 |
| 续办 | 最后完成阶段、下一步、所需输入或授权、回退方案 |

资料引用必须指向实际存在的文件；未生成的产物明确记录“未生成”，不得填入看似完成的路径。批次编号和条目编号是维护标识，不代替商品 ID。

### 13.3 汇总报告模板

每个输入占一行；分类和验收分列，不能将“属于插件”写成“可以使用”。

| 编号 | 原始名称 | 判定类型 | 依据 | 规范化副本 | 改造摘要 | 验收结果 | 商品 ID | 注册结果 | 阻塞与下一步 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 待填 | 待填 | 插件／独立技能／连接器／待判定 | 待填 | 未生成或实际路径 | 待填 | 通过／失败／未执行／不适用 | 未分配或实际 ID | 已注册／未注册／重复跳过 | 待填 |

报告末尾必须列出：

1. 输入总数、拆包后条目数及各类型数量。
2. 已注册、阻塞、重复跳过、排除及其他未完成项数量，统计能够对齐清单。
3. 实际修改的项目文件及生成资源位置。
4. 实际执行的检查、测试、结果与证据。
5. 是否进行个人安装、Git 提交或共享发布；未执行则明确说明。
6. 下一会话从哪个条目、哪个阶段继续，以及还缺什么。

### 13.4 续办与幂等规则

新会话续办时：

1. 读取当前项目规则、两份规范、批次清单和报告。
2. 核实目标项目、输入和规范化副本存在，验证哈希及已有市场实际状态。
3. 已注册且资源未变的条目不重复改造、打包或安装；只做必要的一致性检查。
4. 已完成改造但未验收的条目从验收继续；未改造或被阻塞的条目从对应阶段继续。
5. 输入、规范、依赖、改造内容或最终交付有变化时，重新执行受影响的审核和验收，并保留此前记录。
6. 清单写已注册但磁盘未注册时，不按报告直接判成功；核实后补齐或纠正记录。磁盘存在但清单缺失时也先确认来源，不重复创建。
7. 同标识已存在但版本或内容不同，按更新冲突处理，不擅自覆盖、卸载或删除。
8. 清单或原始资料缺失时先恢复事实；无法恢复则列为阻塞，不凭前一会话总结猜测完成状态。
